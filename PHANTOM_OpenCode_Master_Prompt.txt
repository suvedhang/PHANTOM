Product Mission and Differentiation

PHANTOM observes a physical scene, represents entities and their
relationships over time, evaluates configured or learned scene-specific
rules, and emits explainable events. The product should answer four
questions: What did the vision system observe? What changed? Which rule
was violated? What action or investigation should follow? Do not market
the system as predicting every possible anomaly. Describe the first
release as explainable visual rule monitoring with optional baseline
statistics. Use the term anomaly carefully and attach it to a defined
rule, baseline deviation, or measurable heuristic. Build an explicit
distinction between detection, tracking, scene interpretation, rule
evaluation, event creation, and notification. Do not let an LLM invent
the evidence behind an event. If any natural-language explanation is
added, generate it from structured event facts and keep a deterministic
fallback. The rule engine must be deterministic for the first demo. The
system should support a fixed-view camera scene such as a workshop, lab,
corridor, or tabletop workflow. Users must be able to define regions and
rule thresholds from the interface. A rule can specify entity classes,
region membership, direction, dwell duration, sequence order, count
threshold, or expected movement pattern. Each event must include its
rule identifier and version. Each event must include a time range or
timestamp and the relevant track identifiers when available. Each event
must distinguish observed facts from derived estimates. Each event must
expose a confidence or evidence quality field only when a meaningful
source value exists. Do not convert detector confidence into calibrated
event probability. Do not call a heuristic score a probability unless it
is calibrated and validated. Make rule evaluation inspectable in the UI.
Allow an operator to acknowledge, resolve, dismiss, and annotate an
event. Preserve the original event evidence when the operator changes
its status. Keep a complete event audit trail. Support video replay for
local files and the event timeline where feasible. If event clips cannot
be generated by the real pipeline, show the limitation and retain
metadata and timestamps. Do not claim a learned normal baseline exists
until baseline observations have actually been collected. Provide a
setup workflow to define or collect a baseline. Make the baseline
optional; deterministic manually configured rules must work without it.
Demonstrate at least three rule types with repeatable test videos. At
least one rule must be temporal, not merely a single-frame class check.
At least one rule must use movement or track history. At least one rule
must produce a structured external event.

Initial Rule Templates

Exit — trigger when an entity leaves a configured safe polygon.
